# Grok Bot host mapping

This page maps the reference architecture onto Grok Bot. For each concept it states what Grok Bot provides, whether Grok Bot enforces it, how this repository uses it, and what the host or operator must still do. It describes Grok Bot **as documented on 2026-10-26**. Product behavior and menu names change, so re-check the official pages before relying on a row.

Every product claim comes from the [Grok Bot platform facts](platform-facts.md), which links to the official pages. Items from community sources are marked as community. Nothing on this page has been run on a real Grok Bot account; see [Not verified](#not-verified).

## Per-role permissions

All Bots on one account share the same computer, files, browser sessions, app logins, and connected apps. A Bot has no identity of its own; it acts as the signed-in member ([Overview](https://docs.x.ai/grok-bot/overview), [Security](https://docs.x.ai/grok-bot/security)).

**Consequence:** the per-role tool allowlists in this repository describe intent. On Grok Bot they are **not enforced per Bot**. A Bot named "Inbox" can reach the same files and apps as a Bot named "Engineering" if the member can.

The enforced levers that exist are:

- **Per-action approval:** Allow once, Always allow (can save a matching rule), or Deny. It controls the proposed action, not work already done ([Security](https://docs.x.ai/grok-bot/security)).
- **Local execution policy:** Ask every time (member default), Always allow, or Never allow. xAI recommends Never allow unless a Bot needs local files ([Security](https://docs.x.ai/grok-bot/security)).
- **Auto Review:** an independent model that evaluates risky actions (shell commands, app calls, computer use, automation writes, delegation) and can allow, ask, or deny. Custom **Ask first** rules always stop matching actions and win conflicts. Auto Review does not review every side effect: memory writes and most settings changes are named exceptions ([Security](https://docs.x.ai/grok-bot/security)).
- **Enterprise only:** the MCP allowlist (effective only when **Apply to MCP servers** is on) and network allowlists ([Security](https://docs.x.ai/grok-bot/security), [Teams and enterprises](https://docs.x.ai/grok-bot/teams-and-enterprises)).

Options that give real separation, with their limits from the source:

- **Separate accounts:** each user gets a dedicated cloud computer, and users cannot reach each other's computers ([Teams and enterprises](https://docs.x.ai/grok-bot/teams-and-enterprises)). That separation is per person, not per Bot, and it means separate sign-ins and separate members' access.
- **Team Bots:** the platform facts do not describe their isolation or limits, so this page states none. Verify them before choosing this option.

## The approval-runtime example

The [approval-runtime example](../../../examples/approval-runtime/README.md) does **not** run inside Grok Bot. Grok Bot's native approvals are the gate on that host, and the example is not wired into any Bot.

It remains a conformance reference for hosts that embed their own runtime. It shows the lifecycle such a host must enforce: bind an approval to an exact action digest and revision, authenticate the decider outside agent-written text, persist `executing` before a side effect, and mark an ambiguous outcome `outcome_unknown` instead of retrying. Its file store is single-process, and its callbacks are not a security control.

## Not verified

Nothing below has been checked on a real Grok Bot account:

- Any behavior described in the table, including how a Bot reads and writes `/workspace` in practice when several Bots write at once.
- Plugin install of this repository's skills, from the Cursor marketplace or a team marketplace. The only plugin example is a community source.
- Whether a per-action approval rule can be scoped to a single Bot.
- Team Bots: isolation, limits, and approval behavior.
- Audit and team-control features beyond the Enterprise allowlists.
- Routine behavior in practice: pause after a long absence, the 20-run history, and whether scheduled runs honor the approval boundary.
- Group-chat coordination on a board, and whether a coordinator Bot respects one owner per stage.
- Model selection and numeric Bot limits, which the platform facts do not document.

The mapping is a reference for an operator to verify, not evidence that these paths work. The roadmap's real-account walkthrough (E1) is where that evidence would be recorded.
